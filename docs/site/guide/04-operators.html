    Operators & Arithmetic​

    The full C++ operator set with C++ precedence, minus the undefined behavior: integer overflow raises a catchable error instead of wrapping silently, division by zero raises on ints and floats, and nothing in the arithmetic core is UB.

    <=> returns a negative, zero, or positive ordering:

    • Numbers and text compare by value.
    • bool orders false before true.
    • Arrays and vectors compare lexicographically.
    • Maps compare ordered key/value entries, keys by the map's own key rules (a class value key by its class, Key types).
    • Shared/weak handles and function values compare identity.
    • References compare their referents.

    A class supplies its own operator<=>, and an explicit relational operator wins over rewriting through it. Float <=> treats signed zeros as equivalent and places all NaNs after numbers, while ordinary float equality and relational operators keep IEEE behavior.

    String + joins text ("a" + "b"), and a char beside a string is its character, as in C++ ("ab" + 'c' is "abc", 'c' + "ab" is "cab"). An object beside a string joins its text (its class's to_string()), unless its class declares an operator+ that takes the string. += onto a string appends strings and chars and raises on anything else.

    A number, bool or null beside a string is an error, in either order. "a" + 5 fails with cannot apply '+' to 'string' and 'int': stringify it with to_string(x) or `${x}`, at load where the checker knows both types and at run time otherwise. Write "a" + to_string(n), or a template string `a${n}`, whose splices are text.

    Comparison on strings is lexicographic, and a char compared with a string compares as its one-character string (below). char operands promote to int (unsigned, 0–255) in every numeric context (see below).

    Arithmetic, precedence, inc/dec​

    jaiscript
    print("7 / 2   = {}", 7 / 2);         // int / int stays int
print("7.0 / 2 = {}", 7.0 / 2);       // any float operand promotes
print("7 % 3   = {}", 7 % 3);
print("2 + 3 * 4 = {}", 2 + 3 * 4);   // usual precedence
auto x = 5;
print("x++ = {}, then x = {}", x++, x);
print("--x = {}", --x);
-x;
    output
    7 / 2   = 3
7.0 / 2 = 3.5
7 % 3   = 1
2 + 3 * 4 = 14
x++ = 5, then x = 6
--x = 5
== result: -5

    Comparisons, <=>, short-circuit​

    jaiscript
    print("3 <=> 7  = {}", 3 <=> 7);      // spaceship: -1 / 0 / 1
print("7 <=> 7  = {}", 7 <=> 7);
print("9 <=> 7  = {}", 9 <=> 7);
print("\"a\" < \"b\" = {}", "a" < "b");
print("1 == 1.0 = {}", 1 == 1.0);
auto side_effects = 0;
function tick() { side_effects += 1; return true; }
auto r = false && tick();             // short-circuit: tick never runs
print("side_effects = {}", side_effects);
true || tick();
side_effects;
    output
    3 <=> 7  = -1
7 <=> 7  = 0
9 <=> 7  = 1
"a" < "b" = true
1 == 1.0 = true
side_effects = 0
== result: 0

    Float comparisons follow IEEE: a NaN operand makes ==, <, <=, > and >= false and != true, on every path (a condition, a loop head, an array compared element by element). <=> supplies a total numeric order: signed zeros are equivalent and all NaNs form the final equivalent group. Default float sorting uses this order. Map keys keep their separate total order, so a NaN key is found again.

    Null: ?., ?? and ??=​

    x?.member is null when x is null, and the rest of the chain after it is skipped: x?.a.b, x?.items[0] and x?.f().g() are all null for a null x. Only the value in front of the ?. is tested, as in JavaScript and C#: a null x.a still raises at .b, so a nullable link needs its own ?..

    a ?? b is a when it is not null and b otherwise, and b runs only then. 0, false and "" are values, not null. a ??= b assigns b only when a holds null, and its value is what a holds afterwards:

    jaiscript
    class Weapon { string name = "axe"; }
class Hero { var weapon = null; }
Hero bare;
Hero armed;
armed.weapon = Weapon();
var nobody = null;
print(bare.weapon?.name ?? "fists", " ", armed.weapon?.name ?? "fists", " ", nobody?.weapon.name ?? "no hero");
var settings = {"volume": 7};
print(settings["volume"] ?? 5, " ", settings.get("music") ?? 5, " ", 0 ?? 5);
var cache = null;
cache ??= [1, 2];
cache ??= [9];
print(to_json(cache));
    output
    fists axe no hero
7 5 0
[1,2]

    ?? binds more loosely than || and more tightly than ?:, and groups to the right: a ?? b || c is a ?? (b || c) and a ?? b ? x : y is (a ?? b) ? x : y.

    A missing map key raises when read (Maps), so m.get(k) ?? fallback reads a default without inserting (m.get(k, fallback) says the same), and m[k] ??= v needs the key to be there. The target of ??= is read and then perhaps stored, so it is a variable, a member or an element whose index runs no code. a[i++] ??= v is an error at load that asks for a local.

    Evaluation order is a contract​

    C++17's order: the callee before its arguments, the arguments left to right, and in an assignment the right side before every part of the target.

    In a call, the callee expression is evaluated before any argument, and arguments go left to right. Binary operators evaluate their left operand first. This is the C++17 rule, it holds on both backends, and it is the order errors surface in too: if the callee and the first argument both fail, you see the callee's error.

    jaiscript
    function a() { print("argument a"); return 1; }
function b() { print("argument b"); return 2; }
function add(x, y) { return x + y; }
function pick() { print("callee"); return add; }
print("sum = ", pick()(a(), b()));
    output
    callee
argument a
argument b
sum = 3

    Why it matters: a callee expression that reads a global runs before an argument that changes it, and a side effect in argument two never precedes one in argument one. You can rely on that, in either backend, rather than hoping.

    Each argument also takes its value when it is evaluated, as in Lua, Python and JavaScript. A later argument that writes a variable, an element or an object an earlier argument read does not change what the callee receives. A reference parameter binds the storage itself, so it sees the write:

    jaiscript
    var scores = [10, 20, 30];
function bump() { scores[1] = 99; return 1; }
function add(x, y) { return x + y; }
function add_ref(int& x, y) { return x + y; }
print("by value:     ", add(scores[1], bump()));
scores[1] = 20;
print("by reference: ", add_ref(scores[1], bump()));
    output
    by value:     21
by reference: 100

    A reference parameter binds when its argument is evaluated, as in C++. The object a field argument reads from and the index an element argument names are the ones evaluation saw. A later argument that reassigns the receiver or moves the index changes what the variables hold, never which storage the parameter names:

    jaiscript
    class Counter { int n = 0; }
var first = new Counter();
var second = new Counter();
var c = first;
var hits = [0, 0];
var i = 0;
function inc(int& x, y) { x += 1; return y; }
inc(c.n, c = second);   // binds first.n, then c changes
inc(hits[i], i++);      // binds hits[0], then i moves
print(first.n, " ", second.n, " ", hits[0], " ", hits[1]);
    output
    1 0 1 0

    Assignment runs the other way, again as in C++17: in target = value and target op= value the right side is evaluated first, then the target. That means:

    • For obj.f op= e, this.f op= e, C::s op= e and ns::x op= e: e, then the receiver, then the member's read (a user getter included), the arithmetic and the store.
    • For a[j] = e and a[j] op= e: e, then a, then j, then the element.

    An error in the right side is the one you see, and the target is never touched:

    jaiscript
    string log = "";
class Box { int v = 1; }
shared_ptr<Box> b = new Box();
function target() -> shared_ptr<Box> { log += "target "; return b; }
function value() -> int { log += "value "; return 5; }
target().v += value();
print(`${log}-> ${b.v}`);
    output
    value target -> 6

    Chars promote like C++​

    A char operand enters every numeric context (arithmetic, bitwise, and comparisons, the unary -, + and ~ included) as an integer in 0–255, always unsigned (signed char is a binary-data footgun this language opts out of). s[i] reads a char from a string, so byte-level parsing is ordinary arithmetic:

    jaiscript
    var s = "abc";
print("'z' - 'a'  = {}", 'z' - 'a');
print("s[1] == 'b': {}", s[1] == 'b');
print("s[0] == 97:  {}", s[0] == 97);
print("s[0] + 0   = {}", s[0] + 0);
print("'a' & 0x7F = {}", 'a' & 0x7F);
type_of('a' + 1);
    output
    'z' - 'a'  = 25
s[1] == 'b': true
s[0] == 97:  true
s[0] + 0   = 97
'a' & 0x7F = 97
== result: int

    Compound assignment and ++/-- promote the same way, wherever the char is held: a var local, field or element holding 'b' holds the int 97 after -= 1 and 99 after ++. A variable declared char refuses the int (Cannot assign int to 'c' (declared char), a load error when the checker sees it).

    Beside a string a char is text, never a number: it compares as its one-character string under every comparison, in either order, so s[i] == "x" holds when byte i is x. A string of any other length compares as text too: 'a' == "ab" is false, 'a' < "ab" is true and the empty string sorts before every char.

    s + 'c' and 'c' + s join, as s += 'c' appends. A char variable, parameter, field, element or return takes a string of exactly one character, and a string one takes a char as its text (the conversion table). A switch over either matches the other's cases. In a map a char key and its one-character string are one key (Maps):

    jaiscript
    string word = "banana";
int count = 0;
for (auto ch : word) { if (ch == "a") { count++; } }
char first = "b";                  // a one-character string fills a char
print("{} a's, starts with {}: {}", count, first, word[0] == first);
print(word + '!', " ", 'a' < "ab", " ", 'a' == "ab");
switch (word[2]) {
    case "n": print("n at 2"); break;
    default: print("something else");
}
try { char two = word.substr(0, 2); } catch (e) { print("caught: {}", e); }
    output
    3 a's, starts with b: true
banana! true false
n at 2
caught: Cannot convert 'string' to 'char': a char takes a string of exactly one character

    A literal of another length into a char is the same text at load: char c = "ab"; fails with cannot initialize 'c' declared 'char' with 'string': a char takes a string of exactly one character.

    Arithmetic stays numeric, and there is no implicit int→char either: 'a' + 1 is the int 98, "a" + 1 is the + error above, and char c = 65 is a type error.

    The char↔int door is cast<T> (cast<char>(n) for an int in 0..255, cast<int>(c) for the code point), with to_char(n) as the stdlib function form of the same range-checked rule, and \xNN literals for bytes you know at write time:

    jaiscript
    char c = cast<char>(65);          // int -> char, range-checked 0..255
int  n = cast<int>('a');          // char -> int: the code point
print(c, " ", n, " ", cast<string>('z') + "!", " ", cast<char>("q"));
print(to_char(66));               // the stdlib function form of the same rule
try { var bad = cast<char>(256); } catch (e) { print("caught: ", e); }
    output
    A 97 z! q
B
caught: Cannot cast 'int' to 'char'

    The byte-work recipes (s[i] - '0', little-endian words, out += to_char(b)) are in Containers & Strings.

    Checked overflow: raises, never wraps, never UB​

    The default build policy is JAISCRIPT_CHECKED_OVERFLOW ("safe by default"): overflowing + - *, unary -, and INT64_MIN / -1 raise a catchable run-time error. The alternative build policy (JAISCRIPT_WRAP_ON_OVERFLOW) wraps two's- complement instead. Either way, integer arithmetic is never undefined behavior. Internally it is computed in unsigned. engine::throw_on_overflow() reports which policy the build uses.

    jaiscript
    auto big = 9223372036854775807;   // INT64_MAX
try {
    big = big + 1;                // checked overflow raises, never wraps or UB
} catch (e) {
    print("caught: {}", e);
}
big;
    output
    caught: Integer overflow in '+'
== result: 9223372036854775807

    Note the value is untouched after the failed operation. ++/-- are covered by the same policy, as are the intermediate results of compound assignments.

    When wraparound is the point (a hash, a checksum, a random generator), say so: math::wrap_add(a, b), math::wrap_sub(a, b) and math::wrap_mul(a, b) compute the two's-complement result modulo 264 in every build, with no mask to keep a product small, and the result of a shift << / >> always wraps (the count must be 0 to 63, else Shift amount must be between 0 and 63). An FNV-1a hash:

    jaiscript
    int h = -3750763034362895579;             // the FNV-1a offset basis, 0xcbf29ce484222325, as an int
for (auto c : "abc") {
    h = math::wrap_mul(h ^ c, 1099511628211); // the FNV prime; the product wraps modulo 2^64
}
print("fnv1a(\"abc\") = {}", h);
    output
    fnv1a("abc") = -1792535898324117685

    Division by zero​

    Both integer and float division by zero raise a catchable error (floats do not produce IEEE infinity):

    jaiscript
    try {
    auto x = 1 / 0;
} catch (e) {
    print("int:   caught {}", e);
}
try {
    auto y = 1.0 / 0.0;    // float division by zero also raises (no IEEE inf)
} catch (e) {
    print("float: caught {}", e);
}
"still running";
    output
    int:   caught Division by zero
float: caught Division by zero
== result: still running

    Equality: memberwise values, pointer-compared handles​

    == and != compare values memberwise, the way C++ containers do: arrays element by element, maps entry by entry in key order, class instances field by field, each stopping at the first difference and short-circuiting on a size or class mismatch. A class that defines operator==, or operator<=> (below), takes precedence, for itself and wherever it appears as an element or a field.

    A shared_ptr handle compares like std::shared_ptr, by pointer: two new objects with equal fields are not equal, a handle equals itself and its aliases. Identity for everything else is a separate question, asked with same_object(x, y): references resolve to their referents, handles to the object they share, and containers and instances are the same object only when they are one allocation. Primitives and strings carry no identity, so same_object compares them as values.

    jaiscript
    class Stats { int hp = 10; array<int> buffs = [1, 2]; Stats() {} }
Stats a = Stats();
Stats b = Stats();                 // a second value with the same fields
Stats c = Stats(); c.buffs.push(3);
print("values:  {} {}", a == b, a == c);
print("arrays:  {} {}", [1, [2, 3]] == [1, [2, 3]], [1, 2] == [1, 2, 3]);
print("maps:    {}", {"x": 1, "y": 2} == {"y": 2, "x": 1});
var h1 = new Stats();
var h2 = h1;                       // a var copy of a handle shares it
var h3 = new Stats();              // a different object with equal fields
print("handles: {} {}", h1 == h2, h1 == h3);
print("identity: {} {} {}", same_object(a, b), same_object(h1, h2), same_object(a, a));
    output
    values:  true false
arrays:  true false
maps:    true
handles: true false
identity: false true true

    Map keys compare under the map's own ordering, so {1: "a"} and {1.0: "a"} hold different keys and are not equal even though 1 == 1.0. Arrays and maps also order lexicographically under <, <=, >, >= and <=> ([1, 5] < [2] is true). A class instance has no builtin order: a < b on two instances raises Invalid operands for < operator unless the class declares operator< or operator<=> (below).

    Values compare at any depth (the comparison walks them on a work list, not the native stack). A cycle cannot arise, since a value cannot contain its owner and handles compare by pointer.

    Operator overloading​

    C++'s overloadable set and C++20's comparison rewriting: declare operator<=> and <, <=, >, >= follow, and == too when no operator== takes the operand. There is no operator!: as with explicit operator bool, one conversion, to_bool(), answers both !v and if (v).

    Script classes define operators as methods, with class instances or even primitives on the right-hand side. C++-bound classes get the same treatment through dynamic_binder (see Embedding). One detail worth knowing: an operand that flows into your operator arrives as written. A char is not promoted on the way in.

    jaiscript
    class Vec {
    int x = 0; int y = 0;
    Vec(int px, int py) { x = px; y = py; }
    Vec operator+(Vec other) { return Vec(x + other.x, y + other.y); }
    bool operator==(Vec other) { return x == other.x && y == other.y; }
    Vec operator*(int k) { return Vec(x * k, y * k); }
}
auto a = Vec(1, 2);
auto b = Vec(3, 4);
auto c = a + b;
print("a + b = ({}, {})", c.x, c.y);
print("equals: {}", c == Vec(4, 6));
auto d = a * 3;
print("a * 3 = ({}, {})", d.x, d.y);
    output
    a + b = (4, 6)
equals: true
a * 3 = (3, 6)

    The overloadable set is C++'s, less &&, ||, the comma, -> and new/delete: binary + - * / % & | ^ << >> < > <= >= == != <=>, unary - + ~, and =, [], (). The parameter count tells a unary operator from a binary one, as in C++: operator-() negates, operator-(Vec other) subtracts.

    • When your operator runs. Your operator runs when its left operand (a unary operator's only operand) is an instance of the class or a subclass. The exception is == and != in a class without <=>, which answer only values of the class (below). Every other operand keeps the builtin meaning, and an operator the class does not declare raises the builtin text (-v without operator-() is Unary minus requires numeric operand).
    • Your operator beats a builtin meaning. As in C++ overload resolution, your operator beats a builtin meaning the operands also have: with string operator+(string s), v + "!" runs it instead of concatenating. When no overload takes the right operand (only operator+(Vec other)), v + "!" is the builtin concatenation of v's text.
    • Assignment. An operator= runs on every = into an existing object of the class whose overloads take the right-hand value. That holds in a variable, field, static, element or map value declared the class or in a var. A declaration, a parameter and a return copy-construct instead (Classes).
    • Compound assignment. A compound assignment is the binary operator and a store: a %= b is a = a % b through your operator%, with no separate operator%= in a script class. A C++ class can bind one, which then runs in place; see the dynamic binder.
    • Truthiness. There is no operator!. As with a C++ operator bool, !v and if (v) go through the one conversion, to_bool(), so !v is !to_bool(v) and the two never disagree. Declaring operator! is a parse error that says so (operator! cannot be declared: !v is !to_bool(v); declare bool to_bool()). An instance of a class without to_bool() is truthy, like any non-null value.
    jaiscript
    class Bits {
    int v = 0;
    Bits(int x) { v = x; }
    Bits operator&(Bits o) { return Bits(v & o.v); }
    Bits operator|(Bits o) { return Bits(v | o.v); }
    Bits operator<<(int k) { return Bits(v << k); }
    Bits operator~() { return Bits(~v & 255); }
    bool to_bool() { return v != 0; }
    Bits operator-() { return Bits(0 - v); }
    int operator<=>(Bits o) { return v < o.v ? -1 : v > o.v ? 1 : 0; }
}
Bits flags = Bits(5);
flags |= Bits(8);
flags <<= 1;
print("{} {} {} {}", flags.v, (~flags).v, !Bits(0), (-flags).v);
print("{}", Bits(3) <=> Bits(7));
    output
    26 229 true -26
-1

    The comparisons follow C++20's rewriting. A class that declares operator<=> gets <, <=, > and >= from it: a < b is (a <=> b) < 0, a >= b is (a <=> b) >= 0, the result (an int or a float) compared with zero. Equality comes from it too, and sort() orders through the same <.

    The exact rules.

    • A declared operator wins. An operator the class chain declares wins over the rewrite for an operand one of its overloads takes. A class with its own operator< keeps it and takes the other three from <=>. With operator<(Version o) and operator<=>(int m), v < 5 is the rewrite.
    • Any operand, both orders. <=> drives every comparison it can take, against any operand and in both orders. The right operand answers when the left one has no operator for it: 5 < v is 0 < (v <=> 5) and 5 <=> v is 0 <=> (v <=> 5), in the builtin order (a NaN result orders last).
    • Equality. When an operand's chain declares <=>, a == b is that class's operator== if one of its overloads takes the other operand, else (a <=> b) == 0, the left operand first, then the right one. So price == 500 and 500 == price both work with an operator<=>(int), and two values of the class compare through it in place of the memberwise default (above).
    • Inequality. a != b is !(a == b), unless the class declares operator!=, and x == null stays a null test.
    • No overload takes the operand. An overload counts only when its parameter takes the other operand. Otherwise the builtin meaning stands (Invalid operands for < operator, or == false).
    • Equality without the rewrite. A class without <=> compares against values of the class, through its operator== or operator!= when it declares one, memberwise otherwise. It also compares against any operand one of its overloads with a typed parameter takes, from either side as C++20 reverses ==: with operator==(int n), v == 3 and 3 == v both run it. Against any other operand == is false and != true.
    • Bound C++ classes. A bound C++ class compares the same way through the operators its binding registers. One that binds neither == nor <=> compares its values by identity, the same object only.
    jaiscript
    class Version {
    int major = 0; int minor = 0;
    Version(int a, int b) { major = a; minor = b; }
    int operator<=>(Version o) { return major != o.major ? major - o.major : minor - o.minor; }
    int operator<=>(int m) { return major - m; }   // against a bare major number
}
Version v1 = Version(1, 4);
Version v2 = Version(2, 0);
print("{} {} {} {}", v1 < v2, v1 >= v2, v2 > v1, v1 <= Version(1, 4));
print("{} {}", v1 == Version(1, 4), v1 != v2);
print("{} {} {}", v2 == 2, 1 < v2, 3 <=> v1);
array<var> versions = [v2, Version(0, 9), v1];
versions.sort();
print("{}.{}", versions[0].major, versions[0].minor);
    output
    true false true true
true true
true true 1
0.9

    An operator() makes instances callable. A call whose callee holds such an instance runs it with the call's arguments, at any arity and with overloads chosen as for any method, whether the instance sits in a local, a global, a field, an array element or a shared_ptr. It keeps its state between calls (more in Classes).

    An operator[] that returns T& makes the subscript an lvalue, so g[i] = v and g[i] op= v store through it. One that returns by value makes g[i] a read, and a store to it raises Cannot assign to a call result: 'operator[]' returns by value (a load error when the checker knows the class):

    jaiscript
    class Grid {
    array<int> cells = [0, 0, 0, 0];
    int& operator[](int i) { return cells[i]; }   // a reference return: g[i] is an lvalue
}
Grid g;
g[2] = 7;
g[2] += 1;
print("{} {}", g[2], to_json(g.cells));

class Adder {
    int calls = 0;
    int operator()(int a, int b) { calls += 1; return a + b; }
}
Adder add;
