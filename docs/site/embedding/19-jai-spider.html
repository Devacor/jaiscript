    jai_spider: a Web Application Host​

    jai_spider serves a JaiScript program as a web application. It is a host like any other on these pages: an HTTP/1.1 server, SQLite bound as a class, and a script library, in tools/jai_spider.

    • The app is a program that ends in spider::spin(routes). Each request goes to the handler it spun.
    • Every request runs in a fresh engine, on a pool of workers. A slow handler delays only its own request, and no request sees what another left in a script global: state that outlasts a request lives in the database or the session.
    • Saved edits apply to the next request. Each engine is built from the app's files as they are; an edit that fails its check is logged and the app keeps serving the code it had.
    • SQL text is always a program constant; values only bind as parameters.
    • It speaks no TLS. Deploy behind a reverse proxy that terminates HTTPS.

    Running an app​

    shell
    jai_spider tools/jai_spider/examples/guestbook/app.jai
/\(o.o)/\  jai_spider 0.6.0-beta
jai_spider: spinning tools/jai_spider/examples/guestbook/app.jai on http://127.0.0.1:8080/ (files from .../guestbook/public)
jai_spider: 8 workers, a fresh engine for each request (the first build took 23.5 ms); edits apply on the next request; Ctrl+C stops
GET / 200 1.21 ms
GET /style.css 200 0.31 ms (file)
POST /sign 303 2.40 ms
jai_spider: reloaded views.jai
GET / 200 1.87 ms

    The jai_spider CMake target builds bin/jai_spider beside the runner (JAISCRIPT_BUILD_SPIDER, on in a standalone build). SQLite's official amalgamation is in the repository, under tools/jai_spider/third_party/sqlite, and is compiled into it: nothing needs installing or downloading. Ctrl+C stops the server and closes every database. In the request log a control or non-ASCII byte of the path is written as \xNN.

    The usual options are --port N (default 8080), --root DIR for the static root and --dev for error pages that show the error. Every option: command-line options.

    A first app​

    jaiscript — app.jai (under jai_spider)
    import "spider.jai";

database db = open_database("notes.db");        // relative to the app's folder
db.execute("CREATE TABLE IF NOT EXISTS notes (id INTEGER PRIMARY KEY, text TEXT NOT NULL)");

spider::router routes = spider::router();
routes.get("/", (spider::request req) => {
    int count = db.value("SELECT COUNT(*) FROM notes");   // what outlasts a request lives in the database
    return spider::html(`<h1>${count} notes</h1>`);
});
routes.get("/notes", (spider::request req) => db.query("SELECT id, text FROM notes"));   // a value answers JSON
routes.post("/notes", (spider::request req) => {
    db.execute("INSERT INTO notes (text) VALUES (?)", req.form()["text"]);
    return spider::redirect("/notes");
});
routes.get("/notes/:id", (spider::request req) => {
    var note = db.query_one("SELECT id, text FROM notes WHERE id = ?", req.param("id"));
    return note == null ? spider::not_found() : spider::json(note);
});

spider::spin(routes);

    spider::spin(handler[, options]) (also named spider::serve) takes a spider::router or any function of a spider::request. The options are budget (seconds a request may run) and max_body (bytes), which override the command line from the next request on; any other key raises.

    A handler returnsThe client gets
    a spider::responsethat response
    a string or a web::htmlan HTML page
    null204 No Content
    any other valuethe value as JSON

    Besides the library in lib/, the host registers the full standard library, the runner's file functions, the web:: library, and parse_cookies, parse_multipart, http_date and content_type_for. A page is usually a template, whose splices escape every value; a handler may return the web::html it produces.

    The classes are named in snake_case like the rest of the language: spider::request, spider::response, spider::router, spider::upload, spider::session, spider::session_store and, outside the namespace, database. A variable may share a class's name where the type is written with its namespace (spider::session session = sessions.load(req);). Inside namespace spider a bare name is the class, so a variable there cannot take a class's name, and a variable named database hides the class's constructor call database() in its scope. The samples here keep to req, r, s and db.

    Request and response​

    spider::request is a script class in lib/spider.jai; its source is the reference.

    spider::requestWhat it holds
    method, paththe request line; path percent-decoded and without the query
    query, paramsmap<string, string>: the parsed query, the route's captures
    header(name), cookie(name)one header, in any spelling; one cookie, "" when absent
    body, form(), json()the raw body; its urlencoded or multipart fields; from_json of it

    Every member, uploads included: spider::request.

    spider::response (its members) is the class a handler answers with and a client call returns. lib/spider.jai adds the helpers that build the usual answers:

    spider::html(text), spider::plain_text(text) and spider::json(value) answer a body with its Content-Type, spider::redirect(url) a 303, spider::not_found(text) a 404 and spider::file(path, content_type) a file from disk. Each one's arguments and defaults: response helpers.

    Routing​

    spider::router has get, post, put, patch, delete, any and add(method, pattern, handler). Routes match in the order they were added.

    CaseResult
    /posts/:idcaptures one path segment as req.params["id"]
    /files/*restcaptures the rest of the path
    a HEAD requesttakes the GET route and is answered without its body
    a path only other methods match405 with an Allow header
    no match404
    before(filter)runs ahead of every route: null lets the request through, anything else is the answer (a sign-in check)

    SQLite, injection-proof by construction​

    open_database(path) opens or creates a database file (relative to the app's folder; ":memory:" for a scratch one) and returns a database. Copies share its connection, which closes with the last of them. Files open in WAL mode.

    execute, query, query_one and value take the SQL text first and the values after it, and the text is a constant argument. Text built from data does not load (argument 1 of 'query' is not a constant: SQL text must be a constant; pass values as parameters (?)), and text that reaches the call some other way is refused at run time with SQL text must be a constant; pass values as parameters (?) before SQLite sees it. There is no escape or quote function.

    jaiscript (under jai_spider)
    const string FIND_POST = "SELECT * FROM posts WHERE id = ?";
var post = db.query_one(FIND_POST, req.param("id"));
int changed = db.execute("UPDATE posts SET title = ? WHERE id = ?", title, id);
array<map<string, var>> rows = db.query("SELECT id, title FROM posts WHERE author = ?", author);
var by_name = db.query_one("SELECT * FROM posts WHERE id = :id", {"id": id});   // one map binds by name
int count = db.value("SELECT COUNT(*) FROM posts");
var picked = db.query("SELECT * FROM posts WHERE id IN (?)", [3, 5, 8]);     // an array fills IN (?)
var sorted = db.query("SELECT * FROM posts ORDER BY {} LIMIT 20",           // {} takes one constant choice
                      sql_choose(req.query.get("sort", "created"), ["created", "title", "created DESC"]));
db.transaction(() => {
    db.execute("INSERT INTO posts (title) VALUES (?)", title);
    db.execute("INSERT INTO audit (what) VALUES (?)", "post");
});
    In the textFilled by
    ?the next value. An array expands to one placeholder per element, so IN (?) takes a list of any length (an empty one is IN (), which matches nothing).
    :name, @name, $nameone map value, by key
    {}sql_choose(value, choices), for what a parameter cannot be (a sort column, a direction). It answers the choice equal to value; choices must be constants too. Another value raises sql_choose: the value is not one of: created, title, created DESC. A {} takes nothing else, and a choice cannot fill a ?.
    • Types. Values bind from int, float, bool, string and null. Columns come back as int, float, string (TEXT, and a BLOB as its bytes) or null.
    • Statements are prepared once and kept until the database closes. A constant text of several statements given to execute without values runs them all, which suits a schema.
    • transaction(fn) commits when fn returns and rolls back when it raises, then raises again; inside another transaction it is a savepoint. A transaction takes the database's write lock when it begins (BEGIN IMMEDIATE, from transaction and from begin), so transactions on several connections queue, each waiting up to the busy timeout for its turn, instead of failing: what one reads is still so when it writes. begin, commit, rollback, last_insert_id, changes, in_transaction, is_open and close exist too.
    • Errors are catchable and carry SQLite's message: SQLite error: no such table: posts.

    Typed rows: a class for a table​

    Given a class as a type argument, query and query_one answer records instead of maps, and insert and update write one back. The SQL text is a constant as before, and so is the table's name.

    jaiscript (under jai_spider)
    db.execute("CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, handle TEXT NOT NULL, admin INTEGER NOT NULL DEFAULT 0, tags TEXT NOT NULL DEFAULT '[]')");
class User {
    int id;
    string handle;
    bool admin;
    array<string> tags;
}
const string FANS = "SELECT u.* FROM users u JOIN follows f ON f.fan = u.id WHERE f.artist = ?";
const string FIND = "SELECT * FROM users WHERE id = ?";

array<User> fans = db.query<User>(FANS, artist.id);       // each row a User
shared_ptr<User> one = db.query_one<User>(FIND, id);        // a handle, or null when no row
User fresh = from_json<User>(req.body);
fresh.id = db.insert("users", fresh);                         // the new rowid
one->tags.push("artist");
int changed = db.update("users", one);                        // WHERE id = one->id
    • query<T>(sql, ...) answers an array<T> and query_one<T>(sql, ...) a shared_ptr<T>, null when no row matches; the checker knows both, so fans[0].handel is a load error. Each row is built with T() and each column stored in the field of its name (records): an INTEGER 0/1 fills a bool, an INTEGER a float, a TEXT holding JSON an array, map or class field. A column the class lacks is skipped, so SELECT * keeps working after a migration adds one; a field no column names keeps its initializer. A column that does not fit raises database.query: field 'handle' of 'User' is int, not string (... and cannot be null for a NULL).
    • insert(table, record) writes the record's fields that are columns of the table and answers the new rowid. An INTEGER PRIMARY KEY field holding 0 or null is left out, so SQLite assigns it; a field that is no column is skipped. An array, map or class field is stored as its JSON text. update(table, record) sets every other column the record has, WHERE the table's primary key equals the record's, and answers the rows changed. A record may also be a map<string, var>. A field and a column match by exact name, both ways.
    • The table name is a constant argument (argument 1 of 'insert' is not a constant: a table name must be a constant; a value never names a table, and the same text at run time) and names an existing table. The columns come from the schema, read once and again after any schema change; every identifier in the statement comes from there, quoted, and every value binds.
    • Errors: SQLite error: no table named 'posts', SQLite error: table 'log' has no primary key, which update needs, SQLite error: the record has no field 'id' for the primary key of 'users', SQLite error: the record has no column of 'users' to update besides its primary key.

    Uploaded images​

    The host registers image:: in a build with JAISCRIPT_ENABLE_IMAGE on, so a route can check an upload, scale it and store the result: image::data reads a file's format and size from its header alone, image::load decodes it upright, fit and crop_fill scale it and encode writes a JPEG or PNG with no metadata, so a phone photo's GPS position never reaches the site. The argument is always the image's bytes, never a path, so an upload goes in as it came; a file on disk is image::load(file::read(path)).

    jaiscript
    routes.post("/avatar/:id", (spider::request req) => {
    int id = req.param("id").to_int();   // a number, so the file name below is never a path a stranger wrote
    image picture = image::load(req.files()["picture"].data);
    picture.crop_fill(256, 256);
    file::write("public/avatars/" + to_string(id) + ".jpg", picture.encode("jpeg", 85));
    return spider::redirect("/profile");
});

    Sessions​

    lib/session.jai keeps sessions in a table of the app's database (spider_sessions). The cookie carries only a 256-bit random id (crypto::random_hex(32)); the data stays on the server as JSON.

    jaiscript (under jai_spider)
    import "session.jai";

spider::session_store sessions = spider::session_store(db);

routes.post("/sign-in", (spider::request req) => {
    spider::session s = sessions.load(req);      // the visitor's session, or a new empty one
    sessions.rotate(s);                          // a fresh id once the visitor signs in
    s.set("user", req.form()["name"]);
    s.set("flash", "Welcome back.");
    spider::response r = spider::redirect("/");
    sessions.save(s, r);                         // the row and the cookie, when the session changed
    return r;
});

    spider::session has get(key, fallback), has, set, erase and take (read once, for a message shown after a redirect). spider::session_store has load, save, rotate, destroy and purge_expired, and the fields cookie_name, max_age and secure_cookie (set it behind an HTTPS proxy).

    Reaching other servers​

    jai_spider installs the spider:: client and grants the network permission. spider::catch(url) fetches and spider::sling(content, url) sends; both return a spider::response, which a handler can return as it came:

    jaiscript (under jai_spider)
    routes.get("/weather/:city", (spider::request req) => {
    spider::response upstream = spider::catch("https://weather.example/v1/now?city=" + web::url_encode(req.param("city")), {"timeout": 5});
    if (!upstream.ok()) { return spider::json({"error": "the weather service answered " + to_string(upstream.status)}, 502); }
    return upstream;                              // the upstream answer, passed through as it came
});
    • A call blocks its own worker until the answer arrives or its timeout passes; the other workers serve on. Keep upstream timeouts short: a worker that waits serves no one else.
    • A passed-through answer loses its X-Sendfile header and the headers that describe one connection (Connection, Keep-Alive, Proxy-Connection, TE, Trailer, Transfer-Encoding, Upgrade, Content-Length). Its cookies pass through, so clear cookies when they are not yours to set.
    • Which transport carries the call, and whether it speaks HTTPS, is in The HTTP transport.

    Workers and request isolation​

    One network thread accepts connections, reads requests, serves static files and writes responses. Each complete request goes to a pool of worker threads (--workers N, one per hardware thread by default), and each request runs in an engine of its own, the way a PHP request runs in a fresh process:

    • Requests never wait on one another's handlers. A handler that sleeps, waits on spider::catch or runs a long query holds its own worker; the others go on serving.
    • Every request starts fresh. The engine that answers a request ran the app's top level for that request alone: imports, open_database, the router and spider::spin. When the answer has gone, the engine is destroyed, its databases with it. A script global a handler changes is gone by the next request, so a count, a cache or a signed-in user belongs in the database or the session, never in a global.
    • No request waits for a build while a worker has one ready. Each worker keeps its next engine built ahead, app imported and router spun, and builds the following one right after it answers. Every request still costs a build's work, and a worker rebuilding is not yet free: the server keeps up while requests arrive slower than the workers can build, and past that rate they queue. The startup line names how long the first build took (a cold one); a small app builds in a few milliseconds, one of thousands of lines and dozens of templates in tens.
    • Each engine opens its own SQLite connection (WAL mode, a 5 second busy timeout), so engines never share a connection and need no locks; writers wait their turn in SQLite, and so do transactions, which take the write lock when they begin.
    • Answers on one connection go out in order. A connection holds one request at a time, so pipelined requests are answered in the order they came; requests on different connections run at once.
    • A full house is 503. When every worker is busy, requests wait in a queue (--queue N, 1024 by default); past it the server answers 503 Service Unavailable with Retry-After: 1.
    jaiscript (under jai_spider)
    int visits = 0;                                  // 0 when each request's engine starts

routes.get("/visits", (spider::request req) => {
    visits += 1;                                 // 1, every time: the next request has an engine of its own
    db.execute("UPDATE stats SET visits = visits + 1");
    return spider::json({"global": visits, "stored": db.value("SELECT visits FROM stats")});
});

    The engines of different requests share nothing in script. What the host shares between threads (the console, the HTTP client's transport, the app's source stamps) it serializes itself; the console writes each line whole.

    Background tasks: spider::every​

    spider::every(seconds, fn), at the app's top level, declares a task the host runs in the background: purging expired sessions, expiring unpaid quotes, retrying a webhook.

    jaiscript (under jai_spider)
    spider::every(3600, () => sessions.purge_expired());
spider::every(60, () => {
    db.execute("UPDATE quotes SET state = 'expired' WHERE state = 'sent' AND expires < ?", time::unix_ms() / 1000);
});
spider::every(30, () => {
    // retry the webhook until it succeeds, then stop
    return !send_webhook();
});
    • A run is a request without a client. It runs on a worker in a fresh engine, under the same execution budget, so it sees the database and nothing a request left behind.
    • Its schedule: the first run a period after the server starts, then a period after each run starts. A run never overlaps the task's last one: a run that outlasts its period delays the next until it ends.
    • A failure is logged with the task's place and period (jai_spider: spider::every task 2 (every 60 s) failed:, then the error and its trace), and the schedule goes on.
    • A task stops by returning false. A run whose function returns exactly the bool false is its last: the host logs jai_spider: spider::every task 2 (every 60 s) stopped: it returned false and never schedules it again; nothing, true or any other value keeps the schedule. A stopped task stays stopped across rebuilds while its place and period stay; an edit to its period makes it a new task, and a server restart starts every task again.
    • The declarations follow the code. Each build reads them again, so an edit to a task runs on its next turn; a task keeps its schedule while its place and period stay. A period that is not above 0 raises spider::every: the period must be above 0 seconds, got 0.0.

    Hot reload​

    Since every engine is built from the app's files, an edit applies to the next request with nothing to reload in place. The host remembers which files each engine was built from (modules, includes and templates) by their stamps. Before a worker hands a request to the engine it built ahead, it checks those stamps, one per file; when one has moved, it discards the engine and builds another from the files as they are now.

    What a reload guarantees: the engine hands the host every file it loads with the stamp of exactly those bytes (source_file_observer), so the stamps the host checks and the last good texts it keeps are the bytes that build parsed, and a save that lands while an engine is being built is either part of that build or makes it stale. Only a build that is not stale when it ends is judged, as the last good build or as a failure: one that read an older version and finished late, or caught a file between two writes of a save, judges nothing, and the next build does.

    An edit that fails to parse or check is logged once, and the app serves the code it had until the file is saved again. The host keeps the texts of the last build that checked; while the edit stays broken, engines are built from those texts, written out once into a folder under the app's .cache folder and laid out there as they were around the app (a trace from such an engine names that copy). Saving the file again tries it anew:

    console
    jai_spider: the edit was rejected; serving the code the app had:
static check failed:
views.jai:7:25: error: cannot initialize 'n' declared 'int' with 'string'
    string footer() { int n = "three"; return "..."; }
                            ^
GET / 200 0.84 ms
jai_spider: reloaded views.jai
GET / 200 1.66 ms

    Static files​

    For GET and HEAD, a path that names a file under the static root is served before the app sees the request; a folder serves its index.html. A file is sent with a Content-Type from its extension, a weak ETag, Last-Modified and Cache-Control: no-cache, so a browser revalidates each time (304 when unchanged).

    • A file or folder whose real name starts with a dot is never served, whatever name reaches it (a Windows 8.3 short name such as ENV~1 included), nor is anything outside the root.
    • A request path with a . or .. segment, or a segment that decodes to one holding /, \ or NUL, is answered 400 before the app sees it, so a *rest capture handed to spider::file never climbs out of its folder.

    Errors and limits​

    HTTP/1.1 and 1.0 are served with keep-alive and pipelining, bodies by Content-Length or chunked, and Expect: 100-continue. A connection holds one request at a time: the next request is read once the last response has left, so a connection's answers keep their order whichever workers make them.

    A run-time error or an uncaught throw in a handler answers 500 and is logged; the engine that raised it is discarded like any other, and the next request runs in a fresh one. The limits on bodies, request heads, Host names, timeouts, connections and the queue each answer with their own status. Every failure with its status and logged text: failures and limits.
